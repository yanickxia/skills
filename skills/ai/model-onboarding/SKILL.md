# 模型接入

把模型接到用户指定的服务中，并给出可追溯的兼容性结论。模型在目录中可见、接口返回 200、客户端完整可用，是三个不同的验收层级。

主要面向对话模型。Embedding、rerank、TTS 等模型应验证其实际接口，将不适用的对话协议标记为“不适用”并说明原因。

## 1. 确认接入对象与运行链路

- 区分模型厂商、渠道账号、客户端模型名、上游推理 ID、带日期版本与别名；同名模型在不同账号、地域可能有不同权限和能力。
- 读取目标仓库的 `AGENTS.md` / `CLAUDE.md` 及其链接的模型维护文档，再检查现有相近配置；复用已有鉴权、协议转换、模型目录生成及部署流程。
- 本技能维护通用流程；配置路径、字段枚举、渠道顺位、部署命令等项目事实由目标仓库维护。发现缺失或过时时更新项目文档及其入口，不在技能中复制项目事实，也不依赖某台机器的绝对路径。
- 记录实际请求链路：客户端进程 → 网关 → 上游。核实 base URL、路径前缀、DNS/TLS、代理设置、凭证来源，以及请求从哪台机器或容器发出。
- 确认用户需要的协议、能力和渠道顺位；优先从现有配置与请求中推断，只询问确实影响接入的缺失信息。测试版、preview 与正式版分别标识，升级依据不能只有名称或日期更大。

## 2. 接入前逐项检查三种 API

三个格式都要检查，分别记录上游原生能力与网关对客户端提供的能力。上游只原生支持一种协议时，可以使用项目已有的转换器，但必须验证转换后的结果。

| 用户简称 | 协议 | 常见客户端入口 |
| --- | --- | --- |
| chat | OpenAI Chat Completions | `POST /v1/chat/completions` |
| message / messages | Anthropic Messages | `POST /v1/messages` |
| resp / responses | OpenAI Responses | `POST /v1/responses` |

这些是协议入口示意；上游路径、鉴权头和版本头以该渠道文档及实际配置为准，避免重复拼接 `/v1`。

按 [协议验收清单](references/protocol-checks.md) 执行测试，并遵循以下判定规则：

- 对每个渠道单独探测，再测试网关入口。能选择渠道时固定到待测渠道，并用日志确认实际命中，避免自动回退掩盖失败。
- 每种协议分别给出：上游原生结果、网关原生/转换结果、非流式结果、流式结果、已验证的能力与限制。
- 结果区分“通过、失败、不支持、未验证、不适用”。401/403、网络不通、限流或模型加载失败不能直接判为协议不支持；先核实地址、权限与服务状态。404 也要区分路由不存在和模型不存在。
- 转换能力以实际实现为准。Chat 可用不能推出 Messages/Responses 可用；Responses 的基础生成可用，也不能推出服务端会话状态、内置工具等高级功能可用。
- 在必要协议通过前，不把该接入标记为完成。无法补齐时说明缺口与可用范围；用户已明确允许部分协议时，按其范围接入并保留限制。

## 3. 填写 API 与模型元数据

先查模型属性，再写配置。优先从 [models.dev 的模型数据](https://models.dev/models.json) 或其 [源仓库](https://github.com/anomalyco/models.dev) 按 `模型厂商/模型名` 精确匹配；缺项时用对应厂商的当前官方文档或模型无关的元数据 API 交叉确认。
`https://models.dev/api.json` 用于 Provider 接入信息，不能代替模型属性数据。查询失败、无精确匹配或来源冲突时，记录缺口，不能套用同系列另一个模型的数值。

| 项目 | 要求 |
| --- | --- |
| 标识与来源 | 厂商、模型 ID、版本、渠道映射；保留来源链接、查询日期与精确匹配键 |
| API 协议 | 按目标项目的枚举填写 `api` / `apis` 或等效字段，与实际暴露且验证通过的路由一致；区分首选协议与支持列表 |
| 上下文与输出 | 将来源的 `limit.context/output` 映射到目标 schema 的上下文/输出上限字段；确认单位、输入输出共享预算及渠道/部署限制 |
| 输入输出模态 | 将来源的 `modalities.input/output` 映射到目标 schema；区分模型理论能力与此渠道实际接受的输入形式 |
| 推理能力 | `reasoning`、可用档位/开关/预算、默认行为，以及推理内容与工具调用历史的传递要求 |
| 工具调用 | `tool_call` 或项目对应字段；用工具参数生成 → 返回工具结果 → 继续回答的完整回合验证 |
| 结构化输出 | `structured_output`；区分“回答像 JSON”、JSON mode 与严格 JSON Schema |
| 采样参数 | `temperature` 等参数是否接受并生效；明确与推理模式的互斥或限制 |
| 按需字段 | 项目使用的缓存能力、计价单位、知识截止日期等，均需来源依据；不必凭空补全无关字段 |

能力声明不能超出模型、渠道和当前适配器共同可提供的范围。多渠道限制不同，应使用保守的公共能力，或明确按能力选择渠道，避免长请求回退到容量不足的上游。
“未验证”与“不支持”保留不同的证据状态；机器配置按 schema 省略未知字段或采用保守值，不能用 `0` 冒充未知/无限上下文，也不能把未测能力直接设为启用。

## 4. 检查路由、运行行为与性能

- **模型映射与权限：**客户端别名应落到预期上游版本；检查入站授权、模型访问范围、上游密钥注入与敏感头剥离。凭证通过已有环境变量或 Secret 引用，记录与测试产物脱敏。
- **渠道顺位与回退：**保留用户指定顺序。用可控失败或现有测试验证重试状态码、超时、熔断及最终渠道；不要通过关闭真实上游来制造故障。流式输出开始后的错误不能悄悄拼接另一渠道的回复。
- **参数与多轮：**验证输出长度、system 指令、推理开关、工具结果回传及真实客户端需要的参数；必要的参数改写应只作用于对应渠道/协议。
- **流式生命周期：**确认逐步到达、正确结束、取消与中途错误；最终记录中的实际模型、渠道、usage 和完成状态应对应最后一次真实转发。
- **性能：**以小输出、低并发开始，记录首个可见输出延迟、输出 tokens/s、总时长、错误率及样本数。比较渠道时固定输入、输出预算、推理模式、缓存条件和发起位置；需要稳定比较时再增加样本，不能把未收到首字的超时样本剔除后只报成功速度。

小请求通过后，按实际使用场景增加长上下文、多模态或并发测试；不默认打满最大上下文或进行压力测试。区分连接、首字/空闲和整体请求超时，失败重试应有次数或时间上限。

## 5. 同步目录并验收实际客户端

1. 同步模型配置、API 元数据、生成的模型目录，以及必要的映射/协议回归测试。检查 `/v1/models` 或项目模型发现接口中可见的元数据。
2. 用户要求部署时按目标项目流程同步配置或镜像，等待生效；镜像更新与运行配置更新分别核实。仅要求准备接入时，交付可审阅配置和验证结果。
3. 从实际客户端所在主机或容器测试需要的协议。CLI、SDK、后台 daemon 的运行环境可能不同，应核对进程实际使用的 base URL 与凭证来源，不能用新终端的变量替代常驻进程状态。
4. 验收受影响的真实链路：普通回复、流式回复、工具调用和适用的多模态能力。对每个变更的模型/渠道，逐项记录三协议的工具能力；声明支持工具或用于依赖工具的 Agent 客户端时，所有对外承诺支持工具的协议必须通过 **生成结构化调用 → 回传匹配的工具结果 → 继续回答**，非流式与流式分别验收，详见[工具调用验收](references/protocol-checks.md#工具调用验收)。仅返回工具名、第一轮调用成功或 HTTP 200 均不算通过。
5. 工具能力不支持、不适用或尚未验证时写明原因，保持元数据与接入范围一致；工具是用户必需能力时，缺失即接入未完成。确认回退未掩盖问题，保留旧映射或版本用于回退。

## 交付结果

按“模型 × 渠道”给出三协议检查矩阵（含工具非流式/流式完整回合）、元数据来源及缺项、配置改动、实际命中的上游和代表请求证据。
附上适用时的性能数据、部署是否生效、客户端验收结果与回退方式。
未执行的测试标记为“未验证”，部分支持写明限制；目录中可见或单次文本生成成功，不能概括成“三种 API 全部兼容”。
